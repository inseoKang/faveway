# FAVEWAY Dev Log

FAVEWAY 개발 과정에서 발생한 문제, 설계 판단, 구현 변경, 예외 처리 기준을 기록합니다.

완성된 기능 목록을 나열하기보다, **왜 이런 구조를 선택했고 어떤 문제를 어떻게 해결했는지**를 남기는 것을 목표로 합니다.

## 2026-09-14 | 촬영지 데이터 구조 및 초기 API 연결

### 문제

FAVEWAY의 추천과 도슨트 기능이 AI가 임의로 촬영지를 생성하는 구조가 되면 장소 정보의 신뢰성을 보장하기 어렵다고 판단했다.

또한 작품과 장소만 단순 연결하면 특정 배우가 실제 어떤 장면과 어떤 장소에 연결되는지 설명하기 어려웠다.

### 판단

촬영지는 AI가 생성하지 않고, DB에 저장된 검증된 장소 데이터를 기준으로 사용하기로 했다.

핵심 관계:

    Actor
    → Scene
    → Place

작품과 장소의 관계도 별도로 유지한다.

### 구현

도깨비를 기준으로 초기 촬영지 데이터를 정리했다.

- 콘텐츠
- 배우
- 촬영지
- 장면
- Scene ↔ Place 관계
- Scene ↔ Actor 관계
- Content ↔ Place 관계

Supabase 데이터를 읽는 초기 API 흐름을 구성했다.

    Supabase
    → GET /api/contents
    → 콘텐츠 선택 UI
    → GET /api/contents/[contentId]/places
    → 촬영지 표시

### 이슈

`place_relations` 조회 시 permission denied 오류가 발생했다.

### 해결

Supabase 권한 설정을 수정해 콘텐츠와 촬영지 조회가 가능하도록 연결했다.

### 포트폴리오 포인트

AI가 장소 자체를 생성하게 하지 않고, 검증 가능한 DB 데이터를 기준으로 서비스 기능을 구성했다.

추천 기능보다 먼저 **어떤 데이터를 신뢰할 것인지 데이터 구조에서 정의한 경험**으로 설명할 수 있다.

## 2026-09-15 | Planning Flow 및 Trip API 초안

### 문제

콘텐츠를 선택한 뒤 바로 코스를 생성하면 사용자의 여행 가능 시간이나 이동 조건을 반영하기 어렵다.

또한 백엔드 구현 완료를 기다리면 Course UI 개발도 함께 지연될 수 있었다.

### 판단

콘텐츠 선택 이후 별도의 Planning 단계를 두고 여행 조건을 입력한 뒤 Trip을 생성하도록 구성했다.

프론트엔드에서 먼저 개발할 수 있도록 Trip API 요청·응답 구조를 기준으로 화면 개발을 진행했다.

### 구현

    콘텐츠 선택
    → Planning
    → 여행 가능 시간 선택
    → Trip 생성
    → Course

여행 가능 시간 등의 조건을 입력받아 촬영지 후보를 기반으로 Course를 생성하도록 구성했다.

Trip 생성 과정에서는 다음 기준을 확인하도록 했다.

- 활성 상태
- 좌표 존재 여부
- 중복 여부

### Route 계산 초기 방식

실제 보행 경로 API를 연결하기 전에는 장소 간 거리를 Haversine 공식으로 계산했다.

이를 기준으로 다음 값을 계산했다.

- 장소 간 거리
- 예상 도보 시간
- 체류 시간
- 전체 예상 소요 시간

### 이유

실제 경로 API가 준비되지 않았더라도 최종 Course 구조와 UI 흐름을 먼저 검증하기 위해서였다.

### 포트폴리오 포인트

외부 API나 백엔드 구현을 기다리지 않고 **최종 데이터 계약을 먼저 정의해 프론트엔드 개발을 선행한 경험**으로 설명할 수 있다.

## 2026-09-16 | 탐색 구조 확장 — 작품 / 배우 기준

### 문제

작품만 기준으로 탐색하면 사용자가 좋아하는 배우를 중심으로 촬영지를 찾기 어렵다.

반대로 배우만 선택할 경우 배우가 출연한 여러 작품의 촬영지가 한꺼번에 섞이면서 추천 근거가 모호해질 수 있었다.

### 판단

탐색 진입점을 다음 두 가지로 분리했다.

- 작품 기준 탐색
- 배우 기준 탐색

배우와 작품을 함께 선택할 수 있게 해 추천 범위를 사용자가 직접 조정할 수 있도록 구성했다.

### 구현

- 작품 목록 조회
- 작품 제목 검색
- 배우 이름 부분 검색
- 추천 배우 3명
- 작품 → 배우 조회
- 배우 → 작품 조회
- 복수 배우 선택
- 복수 작품 선택
- 작품 미선택 시 선택 배우의 전체 작품 사용
- 작품 전체 촬영지 조회
- 작품 + 배우 촬영지 필터
- 배우 전체 촬영지 조회
- 배우 + 작품 촬영지 필터

### 중복 처리

동일한 장소가 여러 관계를 통해 조회될 수 있어 작품과 장소 관계를 기준으로 중복 데이터를 제거했다.

### 추가 UX

촬영지 목록에서 장소를 선택하면 상세 정보를 확인할 수 있도록 장소 상세 Dialog를 추가했다.

### 포트폴리오 포인트

단순 검색 기능 구현이 아니라 **사용자의 탐색 기준이 추천 결과의 근거와 연결되도록 정보 구조를 설계한 경험**으로 설명할 수 있다.

## 2026-09-16 | Course Map 1차 구현

### 문제

Course가 텍스트 목록으로만 표시되면 사용자가 장소 간 위치 관계와 이동 순서를 직관적으로 이해하기 어렵다.

### 판단

Course 화면에 Kakao Map을 연결하고 Course의 장소 순서를 지도에도 동일하게 표현하기로 했다.

### 구현

- Course 장소 Kakao Map 표시
- 장소 순서를 나타내는 Marker
- 장소 간 연결선
- Course 목록과 지도 순서 동기화

### 이유

지도 UI와 실제 보행 경로 계산을 한 번에 구현하지 않고, 먼저 Course 상태와 지도 상태가 일치하는지 검증하기 위해서였다.

### 포트폴리오 포인트

리스트 UI와 지도 UI가 서로 다른 상태를 가지지 않도록 **하나의 Course 데이터를 기준으로 두 화면을 동기화한 경험**으로 설명할 수 있다.

## 2026-09-16 | Course 편집 기능

### 문제

자동 생성된 Course가 항상 사용자의 최종 선택과 일치하지 않는다.

또한 장소 삭제나 순서 변경이 발생하면 지도와 이동 거리, 예상 시간도 함께 변경되어야 했다.

### 판단

Course를 고정된 추천 결과가 아니라 사용자가 직접 편집 가능한 상태로 구성했다.

### 구현

- 장소 삭제
- 장소 순서 위로 이동
- 장소 순서 아래로 이동
- 변경 후 거리 재계산
- 변경 후 예상 도보 시간 재계산
- 체류 시간을 포함한 Course Summary 갱신

### 상태 흐름

    Course Places 변경
    → 장소 순서 갱신
    → 이동 경로 재계산
    → 거리 계산
    → 도보 시간 계산
    → Course Summary 갱신
    → Kakao Map Marker / Polyline 갱신

### 포트폴리오 포인트

하나의 사용자 액션이 여러 UI와 계산 결과를 연쇄적으로 변경하는 상황에서 **Course 장소 목록을 중심으로 상태 흐름을 정리한 경험**으로 활용할 수 있다.

## 2026-09-17 | Course 상태 저장

### 문제

사용자가 장소를 추가하거나 삭제하고 순서를 변경한 뒤 페이지를 새로고침하면 편집한 Course 상태가 초기화됐다.

### 판단

서버 저장 기능을 붙이기 전 단계에서는 사용자가 편집한 Course 상태를 localStorage에 저장하기로 했다.

### 구현

- 장소 추가 결과 저장
- 장소 삭제 결과 저장
- 장소 순서 변경 결과 저장
- 새로고침 시 Course 상태 복원
- 초기화 기능
- 복원된 Course와 Kakao Map 상태 동기화

### 저장 책임 분리

TMAP에서 다시 조회 가능한 실제 보행 경로 데이터는 localStorage에 저장하지 않도록 분리했다.

저장 대상:

    사용자가 직접 변경한 Course 장소 상태

재계산 대상:

    외부 API를 통해 다시 얻을 수 있는 보행 경로 데이터

### 포트폴리오 포인트

모든 상태를 그대로 저장하지 않고 **사용자 선택 상태와 재계산 가능한 외부 데이터를 구분한 설계 판단**으로 설명할 수 있다.

## 2026-09-17 | TMAP 보행자 경로 API 연동

### 문제

Haversine 공식은 두 좌표 사이의 직선거리를 계산하므로 실제 사용자가 걸어야 하는 길과 거리, 예상 이동 시간을 정확히 반영하지 못한다.

### 판단

지도 UI는 Kakao Map을 유지하고, 실제 이동 거리와 도보 시간 계산에는 TMAP 보행자 경로 API를 사용하기로 했다.

### 구현 구조

    Client
    → POST /api/routes/walking
    → Next.js Route Handler
    → TMAP Pedestrian Route API
    → 실제 거리 / 도보 시간 / 경로 좌표 반환
    → Course Summary 갱신
    → Kakao Map Polyline 갱신

외부 API Key를 클라이언트에서 직접 사용하지 않도록 Next.js Route Handler를 중간 계층으로 두었다.

### 초기 이슈

TMAP API 연결 과정에서 API 인증 및 사용 설정 문제로 요청이 정상 처리되지 않는 상황이 있었다.

### 해결

TMAP API Key 및 관련 사용 설정을 확인하고 수정해 실제 보행자 경로 API 호출이 정상 동작하도록 해결했다.

이후 Course의 인접 장소 간 실제 도보 경로를 조회할 수 있게 됐다.

### 결과

- 실제 보행 거리 적용
- 실제 도보 시간 적용
- 실제 도로 형태를 따르는 Polyline 표시
- Course Summary에 실제 이동 정보 반영

### Fallback

TMAP 요청이 일시적으로 실패하더라도 Course 전체 기능이 중단되지 않도록 기존 Haversine 계산을 fallback으로 유지했다.

    TMAP 성공
    → 실제 거리
    → 실제 도보 시간
    → 실제 보행 Polyline

    TMAP 실패
    → Haversine 거리
    → 추정 도보 시간
    → Course 자체는 계속 사용 가능

### 포트폴리오 포인트

외부 API를 단순 호출한 것이 아니라 다음까지 고려한 **외부 서비스 통합 경험**으로 설명할 수 있다.

- API Key 노출 방지
- 서버 Route Handler 경유
- 실제 경로 데이터와 UI 연동
- 외부 API 실패 시 fallback

## 2026-09-17 | TMAP 경로 요청 구조 개선

### 문제

Course에 여러 장소가 있을 때 각 인접 구간마다 클라이언트에서 별도의 API 요청을 보내면 클라이언트 요청 수가 늘어나고 경로 조회 로직이 화면 코드에 분산될 수 있었다.

예:

    A → B
    B → C
    C → D

4개의 장소가 있으면 3개의 구간 요청이 필요하다.

### 판단

클라이언트에서는 Course 전체 장소 목록을 한 번만 전달하고, 서버 Route Handler가 인접한 장소들을 기준으로 각 구간의 보행 경로를 조회하도록 변경했다.

### 변경 전

    Client
    → A-B 요청
    → B-C 요청
    → C-D 요청

### 변경 후

    Client
    → Course 전체 장소 목록 1회 전달

    Server
    → A-B 경로 조회
    → B-C 경로 조회
    → C-D 경로 조회
    → 구간 결과 통합

    Client
    ← 통합된 Route 결과 수신

### 결과

클라이언트는 전체 Route 계산을 위해 한 번의 요청만 수행하도록 단순화됐다.

TMAP과 관련된 구간 계산 로직도 서버 API 내부로 모아 관리할 수 있게 됐다.

### 포트폴리오 포인트

외부 API 호출 책임을 화면에서 분리하고 **클라이언트와 서버 사이의 인터페이스를 Course 단위로 단순화한 구조 개선 사례**로 활용할 수 있다.

## 2026-09-17 | 공통 UI 구조 및 화면 디자인 정리

### 문제

기능을 순차적으로 구현하면서 각 페이지가 개별적으로 스타일을 가지게 되어
페이지마다 헤더, 이전 버튼, 여백, 색상, 버튼 스타일이 조금씩 달라지고 있었다.

Course, Explore, Planning 등 주요 화면이 하나의 서비스임에도
화면 간 시각적 일관성이 부족했고 공통 UI 수정 시 여러 페이지를 각각 수정해야 했다.

### 판단

페이지별 기능 로직은 유지하면서,
서비스 전반에서 반복되는 스타일과 UI 요소를 공통 구조로 정리하기로 했다.

특히 다음 요소를 공통 기준으로 맞췄다.

- 색상 및 기본 디자인 토큰
- 페이지 최대 너비와 여백
- Header
- BackButton
- 버튼 상태
- 카드 및 Border 스타일
- Loading / Error 등 상태 표현 방식
- 모바일 화면 기준 레이아웃

### 구현

- `globals.css`의 FAVEWAY 공통 스타일 정리
- 공통 `BackButton` 정리
- 공통 `PageHeader` 추가
- Home / Explore / Plan / Planning / Course 화면 스타일 통일
- Place Detail Dialog 디자인 정리
- Course Map / Explore Map UI 스타일 조정
- Course 장소 이동 버튼이 좁은 화면에서 깨지는 문제 수정

기존 데이터 조회, Course 편집, 지도 및 Route 계산 로직은 변경하지 않고
presentation 영역을 중심으로 정리했다.

### 이슈

Course의 장소 선택 chip이 모바일 너비에서 한글 단위로 줄바꿈되거나
다음 버튼이 잘려 보이는 문제가 발생했다.

### 해결

chip 내부 텍스트가 줄바꿈되지 않도록 처리하고,
화면 공간이 부족할 경우 버튼 자체가 다음 줄로 이동하도록 레이아웃을 수정했다.

### 포트폴리오 포인트

기능 구현 이후 화면을 개별적으로 수정하는 대신,
반복되는 UI 패턴을 공통 컴포넌트와 스타일 기준으로 정리해
서비스 전체의 일관성과 유지보수성을 개선한 경험으로 설명할 수 있다.

# 현재 상태 관리 기준

## 기준 상태

Course의 장소 목록을 핵심 기준 상태로 사용한다.

사용자가 직접 변경하는 대상:

- 장소 추가
- 장소 삭제
- 장소 순서 변경

## 파생 상태

다음 데이터는 Course Places가 변경될 때 다시 계산하거나 갱신한다.

    Course Places
    ↓
    지도 Marker
    ↓
    장소 순서
    ↓
    TMAP 보행 경로
    ↓
    Polyline
    ↓
    총 거리
    ↓
    총 이동 시간
    ↓
    Course Summary

이를 통해 각각의 UI가 독립적으로 다른 값을 가지지 않도록 구성한다.

# 외부 서비스 역할 분리

## Supabase

역할:

- 콘텐츠 데이터
- 배우 데이터
- 촬영지 데이터
- 장면 및 관계 데이터

핵심 역할: **서비스의 기준 데이터 저장**

## Kakao Map

역할:

- 장소 위치 시각화
- Marker 표시
- Course 경로 시각화

핵심 역할: **지도 UI**

## TMAP

역할:

- 실제 보행자 경로 계산
- 실제 이동 거리 계산
- 예상 도보 시간 계산

핵심 역할: **경로 계산**

## AI

예정 역할:

- DB에서 확인된 장소 및 작품 정보를 기반으로 사용자 맞춤형 도슨트 설명 생성

  검증된 정보
  - 사용자 취향
    ↓
    AI 설명 생성

AI가 촬영지 자체를 생성하는 역할은 맡지 않는다.

# 아직 정리해야 할 항목

## Loading / Empty / Error 상태

각 API 및 화면에서 다음 상태를 명확하게 분리할 필요가 있다.

- Loading
- Empty
- Error
- Retry

특히 다음 데이터 소스가 함께 존재하므로 전체 페이지 실패와 일부 기능 실패를 구분하는 방향으로 정리할 필요가 있다.

- Supabase
- Kakao Map
- TMAP
- AI API

예:

    TMAP 실패
    ≠
    Course 전체 실패

---

## 데이터 부족 시 Fallback

촬영지 데이터가 부족한 경우 AI가 존재하지 않는 촬영지를 생성하지 않도록 한다.

예상 기준:

    충분한 촬영지 존재
    → 촬영지 기반 Course 생성

    촬영지 부족
    → 사용자에게 범위 확장 여부 확인
    또는
    → 주변 일반 장소 추천

실제 구현 시 최종 정책을 별도로 기록한다.

---

## AI Docent Input

AI 도슨트에는 DB에서 검증된 정보를 중심으로 전달할 계획이다.

예상 입력:

    사용자 취향
    +
    여행 분위기
    +
    장소 기본정보
    +
    작품 정보
    +
    장면 설명
    +
    에피소드
    +
    scene_keywords
    +
    place_keywords
    +
    verified_fact
    +
    source_url

AI의 역할은 **정보 생성**이 아니라 **검증된 정보를 사용자 취향에 맞게 설명**하는 것으로 제한한다.

## API 구조

최종 구현 이후 다음 API를 기준으로 요청·응답 구조를 별도 정리한다.

예:

- `GET /api/contents`
- `GET /api/contents/[contentId]/places`
- 배우 관련 조회 API
- `POST /api/trips`
- `POST /api/routes/walking`

각 API마다 다음만 남긴다.

- 목적
- Request
- Response
- Frontend에서 사용하는 위치
- Error 처리 방식

## 변경 전 / 후 구조

기능이 안정화된 뒤 포트폴리오에서 의미 있는 구조 변경만 선별해서 기록한다.

### Route 계산

변경 전:

    Client
    → 구간별 API 요청

변경 후:

    Client
    → Course 단위 요청
    → Server에서 구간별 Route 처리

### 거리 계산

변경 전:

    Haversine 기반 추정값

변경 후:

    TMAP 실제 보행 경로
    +
    Haversine fallback

    ### 해결

    ### 포트폴리오 포인트
    Frontend Engineer 관점에서
    이 작업이 어떤 역량을 증명하는가?

다음 중 하나라도 해당될 때만 자세히 기록한다.

- 상태 구조가 변경됨
- API 구조가 변경됨
- 사용자 흐름이 변경됨
- 예상하지 못한 오류를 해결함
- 외부 API를 연결함

- fallback / error handling을 설계함
- 나중에 면접에서 설명할 가치가 있는 기술적 판단이 있었음

단순 CSS 수정이나 문구 변경처럼 설계 판단이 거의 없는 작업은 짧게 기록하거나 생략한다.
